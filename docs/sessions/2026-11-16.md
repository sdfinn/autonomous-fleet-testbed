## 2 — Ctrl+C does not stop a real mission

**The issue.** The plan for stopping a real run was Ctrl+C in the terminal running
`robot_boot.sh`.

**How found.** Tested on the Jetson with a harmless container shaped like the real one
(same image, same `docker run … | tee` pipeline, `sleep` in place of the mission) and a
real Ctrl+C sent through an interactive SSH session. 25 seconds later the container and
the script were both still running and the script's cleanup had not run. The container's
first process is a plain bash script with no signal handler, and Linux ignores Ctrl+C
for a container's PID 1 in that case.

**Not fixed.** The working stop is `docker rm -f robot_mission` from a second terminal
(`RealRobotStartup.md` B5 says the same). The driver's 200 ms watchdog then zeroes the
wheels (`esp32_driver.py`, `_watchdog_cb`).

**Lesson.** My first two versions of this test were wrong (a backgrounded test script
ignores SIGINT; then my check ran after the test container had exited by itself). A
test of a safety mechanism needs its own controls checked first.

## 3 — `MISSION2_IGNORE_REACTIONS` never reached the mission

**The issue.** The switch that suppresses ball reactions is read inside the container
(`mission_runner.py:178`), but `robot_boot.sh` did not pass it, so exporting it in the
shell did nothing. In August it only worked through a hand-made debug copy of the script.

**The fix.** `scripts/robot_boot.sh:178`:

```diff
   -e ROBOT_MODE=mission \
+  ${MISSION2_IGNORE_REACTIONS:+-e MISSION2_IGNORE_REACTIONS=1} \
   "$IMAGE" bash /ros2_ws/scripts/container_entrypoint.sh \
```

**Verified.** Unset adds no argument, set adds exactly two; both real runs today used it.

## 5 — The EKF was ignoring the gyro (fixed, verified on the robot)

**Root cause.** The August IMU fix set `angular_velocity_covariance[0] = -1` meaning
"not characterized". `robot_localization` reads −1 there as "ignore the angular
velocity" (its binary contains that message). Commit `bf764d1`, 2026-08-12. This is the
August "hit a wall, then circled" symptom too.

**The fix.** `esp32_driver.py:45` and `:311-313`:

```python
GYRO_VARIANCE_RAD2_S2 = 1.0e-4   # resting z noise measured today: std 0.0028 rad/s
...
msg.angular_velocity_covariance[0] = GYRO_VARIANCE_RAD2_S2
msg.angular_velocity_covariance[4] = GYRO_VARIANCE_RAD2_S2
msg.angular_velocity_covariance[8] = GYRO_VARIANCE_RAD2_S2
```

**Verified.** Mike turned the robot one full turn by hand: gyro (offset removed) −364°,
fused heading tracked the gyro to within 0.2°. That also verifies the gyro scale
(16 LSB/dps), which had been an open item, and the sign (he turned right; negative).

**Lesson.** A "safe placeholder" value can be a command to another library. Check what
the consumer does with it.

## 6 — The lidar's front was wrong twice over (fixed, verified on the robot)

**Root cause.** The lidar is mounted rotated, but its scan was published in a frame with
zero rotation, so Nav2, AMCL and the costmaps saw every wall rotated. Only the smoke
test applied a correction, and that correction (285°) was itself about 16° off.

**How the true bearing was found.** A flat box 0.5 m in front: a line fit to its face
(2.7 mm scatter) is square-on at raw 269.9°. A photo from the robot's own
chassis-fixed camera showed the box square but left of centre, which is why its
edge-to-edge middle (275.7°) was the wrong reading.

**The fix.** `scan_filter.py:58`:

```python
def rotate_scan_frame(angle_min, angle_max, forward_bearing_deg):
    shifted = angle_min - math.radians(forward_bearing_deg)
    new_min = math.atan2(math.sin(shifted), math.cos(shifted))
    return new_min, new_min + (angle_max - angle_min)
```

`scan_masker.py:48`, `:66`, `:102` — default 269°, applied after masking, and the stale
"antenna" sector dropped:

```diff
-DEFAULT_MASK_SECTORS_DEG = [46.0, 123.0, 268.0, 277.0]
+DEFAULT_MASK_SECTORS_DEG = [46.0, 123.0]
+DEFAULT_FORWARD_BEARING_DEG = 269.0
```

The 268–277° sector was the robot's dead-ahead direction; unmasked data showed clean
returns there and Mike's photos show the antenna at the rear. `tools/smoke_test.py:301`
now uses 0, since the scan arrives already corrected.

**Verified.** With 269° the box reads 0.57 m at angle 0.

## 7 — The motor controller thought it was a different robot (fixed on the robot)

**Root cause.** The ESP32's stored start-up commands contained
`{"T":900,"main":3,"module":0}`: UGV Beast (tracked). The robot is a 6-wheel UGV Rover
(main 2). The firmware is `ugv_base_ros` 0.96 (read off the OLED in Mike's photo), not
`ugv_base_general`, which the August protocol notes were built from. In Beast mode it
uses a 52.3 mm wheel and 1092 encoder counts per turn where the Rover has 80 mm and 660,
a ratio of 2.53, and it reverses motor direction. The vendor's own software sends this
command at every start; our driver replaced that software and never did.

| Symptom | Explained by |
|---|---|
| Real speed 2.5× the command, odometry matching the command | The 2.53× mis-scaled speed measurement inside a closed loop |
| Forward and turn both reversed since August | Beast sets `SET_MOTOR_DIR = true` |

**The fix.** Sent `{"T":900,"main":2,"module":0}` over serial, with Mike's go-ahead. The
firmware saves it to flash; to undo, send the old line.

**Verified by lidar, same test before and after (0.10 m/s for 3 s):**

| | Beast setting | Rover setting |
|---|---|---|
| Real distance | 0.725 m | 0.281 m |
| Controller's count | 0.278 m | 0.27 / 0.31 m |
| Direction on a plain forward command | backwards | forwards |

**Driver changes that follow from it** (`esp32_driver.py`):

```python
# :140-151  no sign flips; turn rate scaled for tyre scrub
if self._chassis_ok is False:
    self._send(encode_velocity_cmd(0.0, 0.0))
    return
self._send(encode_velocity_cmd(msg.linear.x,
                               msg.angular.z * self._angular_cmd_gain))
# :238
speed_l = info.speed_l
speed_r = info.speed_r
```

- **Chassis check** (`:193`, `esp32_protocol.py:163`): the driver sends `T:602` at start
  and blocks all motion if the stored type is not 2.
- **Turn gain 2.8** (`:70`): on-the-spot commands of 1.0 / 2.0 / −2.0 / 3.0 rad/s gave
  0.42 / 0.62 / 0.77 / 1.03 by gyro. The six-wheel chassis scrubs its tyres. First-cut
  value, one floor, spins only.

**Verified.** Through the ROS driver: 0.285 m by lidar, 0.273 m by odometry, forwards.

**Lesson.** The August conclusion "this unit is wired backwards" was a wrong explanation
that fit the symptom, and it was compensated instead of questioned. A sign flip in a
driver is a reason to look for a configuration error upstream. And: confirm which
firmware is actually on the device before reading its source.

## 8 — Gyro resting drift (fixed, verified on the robot)

**The issue.** The stationary gyro read +0.26°/s on z, 22° of false turn in 90 s.

**The fix.** `GyroBiasEstimator` (`esp32_protocol.py:108`) learns the offset from each
2-second window in which the wheels report zero, no command is active, and the readings
are quiet and small. The last condition matters because the robot can be turned by hand
with the wheels still. Used at `esp32_driver.py:294`.

**Verified.** 30 s stationary: fused heading change 0.0°.
