**The issue.** 2026-11-18: the Jetson lost power mid-spin and the motor board kept

| Test | Result |
|---|---|
| `tools/bench_stop_on_silence.py` (T:1) | PASS: wheels stopped by themselves 0.45 s after the last command |

regression, and not a stutter.

**Lesson.** Before reading a signal as "the wheels are stopping and starting", find out
how coarse the signal is.

## 3 — Final heading at home (improved, not finished)

**The issue.** The robot arrives home 16-37 deg clockwise of the heading it was asked
for.

**How it was found.** From the bag, the final spin of every leg: the command and the
gyro side by side.

```
t-2.5 s  cmd -0.50  gyro -0.65      <- asked for 0.5 rad/s, already faster
t-1.0 s  cmd -0.81  gyro -0.82      <- the COMMAND has risen
t-0.3 s  cmd -1.15  gyro -1.33
t 0      cmd -0.10  gyro -1.38      <- command ramps down in 0.3 s; the robot has not
```

Nav2's RPP controller clamps each rotate-to-heading command to the *measured* turn rate
plus or minus `max_angular_accel * dt` (3.2 rad/s^2 at 20 Hz = 0.16 rad/s). This robot
turns faster than it is told, so the clamp dragged the command up to "measured - 0.16",
which sped the robot up again. It reached the goal heading at 1.2-1.5 rad/s and it
answers a command about 0.3 s late, so it swept on. (The clamp rule is from memory of
the RPP source, not re-read today; the data fits it: on the stand, where the measured
rate is zero, the command sat at exactly 0.16 for 60 s.)

**The fix.**

```yaml
# src/nav_fleet/config/nav2_params.yaml:175 and :185
      rotate_to_heading_angular_vel: 0.5
      max_angular_accel: 10.0        # was the default 3.2: window +/-0.16 -> +/-0.5 rad/s
```

**Verified on the robot** (lidar scan match at each home stop, three trips each):

| | Before | After |
|---|---|---|
| Heading error at home | 26, 31, 16 deg | 5, 16, 6 deg |
| Highest spin command sent | 1.15 rad/s | 0.82 rad/s |
| Turn rate at the moment of stopping | 1.2-1.5 rad/s | 0.5-1.1 rad/s |

**Not done.** On the 180 deg home spins the robot still peaks at 1.3-1.5 rad/s for a 0.5
command: the tyres break free. The proper cure is closed-loop turn rate in the driver
(gyro feedback) instead of the fixed `angular_cmd_gain: 2.8`.

**Lesson.** A controller that limits its output relative to a *measurement* turns any
actuator that over-delivers into a runaway.

## 4 — The remote stop became a pause (operator watch)

**The issue.** WiFi drops, the Jetson lives, the mission carries on, Ctrl+C goes nowhere.

**Version 1: abort after 2 s without a ping reply, in `robot_boot.sh`.** It stopped the
first run 10 s in. Two faults, found one after the other:

1. *Mine.* It sent one ping at a time with a 1 s wait, so two lost pings made "2 s of
   silence". A healthy link here loses about 1 in 20.
2. *Real.* After a rewrite to one continuous ping (five a second), it tripped again in
   the same place. An independent ping logger running alongside showed a genuine 2.43 s
   gap, and the Jetson's own log showed why:

```
17:44:21 wpa_supplicant: CTRL-EVENT-STARTED-CHANNEL-SWITCH freq=2442
17:44:21 wpa_supplicant: Associated with ec:c3:02:ee:55:e4      (was ...55:ec, 5805 MHz)
```

The WiFi adapter (`rtl88x2ce`) moves between the router's three radios by itself, 12
times between 16:42 and 17:44, and the same change had happened unnoticed in the clean
17:15 run. Pinning the connection to 2.4 GHz (`802-11-wireless.band bg`) put the right
frequency list into wpa_supplicant and changed nothing: the driver roams on its own.

**Version 2 (Mike's design): pause, then resume.**

```python
# src/nav_fleet/nav_fleet/operator_link.py:70-92 (LinkWatch.step, abridged)
if self.state == OK:
    if silence >= self.pause_after_s:          # 2 s
        self._pause(now, events)               # -> PAUSED, two short beeps
elif self.state == PAUSED:
    if self._last_reply > self._paused_at:
        self.state = RESUMING                  # one long beep, wheels still held
        self._resume_at = now + self.resume_delay_s
    elif now - self._paused_at >= self.give_up_after_s:   # 10 s
        self.state = GAVE_UP                   # three low beeps; node exits 3
```

The hold itself is in the motor driver, not Nav2, so Nav2 keeps commanding and simply
carries on:

```python
# src/nav_fleet/nav_fleet/esp32_driver.py:81-86 (HoldInput.state)
if self.time is not None and now - self.time < HOLD_STALE_S:
    return self.value, self.when_true          # the watcher's word, if it is fresh
return bool(required), self.when_silent        # silence holds only if it is mandatory
```

**Verified.**

- No-motion dry run on the Jetson (drivers + watch, pings blocked with a firewall rule):
  held before the watch started; released 0.07 s after it came up; paused 2.0 s into a
  5 s block and released 1.1 s after the link returned; gave up 10.0 s into a 14 s block,
  exit code 3. Watch and driver log the same hundredth of a second. Mike heard all four
  beep patterns.
- On the floor, during trip 2's outbound leg: paused 2.0 s after the block, held 4.6 s,
  released; the leg completed.
- Two real band changes during that run did not pause it (both under 2 s).

**Not verified:** giving up during a real mission. Every deliberate cut I timed from the
console log arrived late, because `tr` block-buffers its output when writing to a file,
so "trip 1 has started" reached my script after trip 1 had ended.

**Lessons.**
- When a watchdog trips, run an independent observer next to it before deciding which
  of the two is wrong.
- A setting that is stored correctly is not a setting that is obeyed: check the
  behaviour (here, the association log), not the configuration.
- A pipe into a file is not live. `stdbuf -oL`, or read the file with something that
  does not sit behind a buffering filter.

## 6 — Ball detection on the real camera (A4: calibrated; not yet run on the robot)

**The issue.** Real runs have had ball reactions switched off because the detector
false-triggers.

**How it was found.** Frames of three croquet balls from both cameras, then the
project's own `detect_balls` on them and on the day's ball-free mission photos:

```
current settings, ball-free marker photo  ->  ('yellow', 5579 px, range 0.04 m)
```

The detector boxed every matching pixel in the frame. The wood floor is inside the
yellow band, so the "ball" was as wide as the picture and 4 cm away. No choice of
colour band fixes that; the calibration tool's own suggestion still matched the floor.

**The fix.** An optional `shape:` section in a camera profile:

```python
# src/nav_fleet/nav_fleet/hsv_detect.py:91-94 (in detect_balls)
if 'shape' in cfg:
    mask = _largest_ball_shaped_blob(mask, cfg['shape'], cfg['min_pixels'])
    if mask is None:
        continue
```

`hsv_gazebo.yaml` has no such section, so the simulator's path is unchanged.

**Which camera.** The front camera (OAK) is dark in evening light but neutral and
usable; the mast camera is brighter but has a yellow cast over everything, reads the
red ball as orange (hue 13, next to the dresser's), and sees the balls at half the
size. Stayed with the front camera.

**Distance scale** (lens to ball front; widths from the new detector):

| Distance | Yellow | Red |
|---|---|---|
| 0.50 m | 162 px | 146 px |
| 0.80 m | 110 px | 99 px |
| 1.05 m | 86 px | 75 px |
| 1.55 m | 59 px | 49 px |

`range_k` 91.8 (yellow) and 80.3 (red), per colour because the red ball's dark rim
drops out of the band. The simulator's 47.1, in use until today, would read a real
ball at half its distance.

**Verified (offline, tonight's frames only).** Both balls found at all four distances.
On 33 ball-free mission photos nothing reads inside a reaction distance: widest false
blob 44 px (reads 2.1 m; yellow reacts at 0.8 m) and 26 px (3.1 m; red at 1.3 m).

**Limits.** One lighting condition; a stationary robot; on the rug the pile hides the
bottom of a ball (yellow measured 110 x 85 px at 0.8 m, aspect 1.29 against a limit of
1.35, and loosening the limit to 1.5 lets a 272 px strip of floor through). Tighter
colour bands lost balls.

**A mistake of mine.** One "reference" frame was labelled 1.05 m but taken after Mike
had already moved the balls to 0.5 m; it showed up as a scale of 175 among values near
90.

**Lesson.** When thresholds will not separate two things, ask what else differs between
them. Here it was shape.

## 7 — Obstacle guard (step 6a: built and replayed; not yet run on the robot)

**The issue.** No collision protection at all on the real robot.

**The fix.** A box 0.25 m ahead of the bumper (behind it when reversing), the robot's
width plus 2 cm a side:

```python
# src/nav_fleet/nav_fleet/path_guard.py:72-85 (PathGuard.in_the_way, abridged)
if linear_x > MOVING_SPEED_MPS:
    gap = pts[:, 0] - self._front_x            # distance ahead of the front bumper
elif linear_x < -MOVING_SPEED_MPS:
    gap = self._rear_x - pts[:, 0]
else:
    return 0, None                             # turning on the spot: not guarded
inside = (gap >= 0.0) & (gap <= self.stop_distance_m) \
    & (np.abs(pts[:, 1]) <= self.half_width_m)
```

Three or more returns inside = held; empty for 1 s = released. It publishes on every
scan and the driver is told the guard is mandatory, so a dead lidar or a dead guard
holds the robot too.

**Verified (replay of recorded scans and commands, before any robot test).**

- Four clean runs, 16 trips including the 0.75 m doorway: zero holds. Nothing came
  within 0.71 m of the bumper while driving forward.
- The 2026-11-18 dresser run: held from 66.0 s, 2.7 s before the contact at 68.7 s.

**The rest of step 6, as laid out for Mike:** 6b stop when pushing against something
(slip verdict); 6c back away and try again; 6d go around (re-plan during a leg); 6e
guard turns on the spot.
