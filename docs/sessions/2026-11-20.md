## 1 — The robot spun on the home spot: the motor board's IMU had not started (fixed)

**The issue.** First run of the day. Nav2 rejected the first goal twice in under 0.1 s
and Mike reported the robot "just spinning around near the home spot".

**How it was found.** Three steps, the first one wrong.

1. *A wrong guess.* The start photo showed a door open that was closed the day before.
   I blamed the map. Mike closed the doors, the rerun started with the same wrong
   position, and the guess was dead. What it cost: one run. What saved the second run:
   a tripwire written in between that stopped the robot the moment Nav2 reported a
   start position more than 0.3 m from home.
2. *The bag.* With the robot standing still:

   ```
   gyro z:       n 450  mean 12.3318 rad/s  std 0.0000    <- 706 deg/s, and frozen
   wheel odom:   x 0.000  y 0.000  yaw 0.000              <- correct
   ekf filtered: yaw 0 -> -44 -> -165 -> 147 -> 109 ...   <- spinning
   amcl_pose:    (-1.276, 1.200, 90 deg) then (-0.06, 3.03) within seconds
   ```
3. *The board itself*, read directly over serial, three seconds, 59 lines:

   ```
   ax 308  ay 31265  az -5042   gx -32253  gy 3840  gz 11305     1 distinct value per axis
   ```
   Gravity reading 3.87 g; `gz 11305 / 16 = 706 deg/s`. The voltage and wheel fields on
   the same line were live, and the magnetometer changed between reads: one chip (the
   accelerometer/gyro) had failed to start at that morning's power-on.

**The fix.** Nothing checked that the IMU was alive. Now three layers do.

*Before* (`esp32_driver.py`, `_dispatch_line`): every status line was published as-is.

```python
            self._publish_odom(base_info)
            self._publish_imu(base_info)
```

*After* (`esp32_driver.py:335-340`):

```python
            self._publish_odom(base_info)
            self._on_imu_sample(base_info)
            # A known-bad IMU is not published at all: silence makes the heading
            # filter coast, garbage makes it spin.
            if not self._imu_bad():
                self._publish_imu(base_info)
```

The judgement (`esp32_protocol.py:187-200`, abridged):

```python
        if len(set(samples)) == 1:                 # ~2 s of samples, all six axes equal
            self.state = IMU_FROZEN
        ...
        g = gravity[len(gravity) // 2] / ACCEL_SENSITIVITY_LSB_PER_G    # the MIDDLE sample
        if IMU_GRAVITY_MIN_G <= g <= IMU_GRAVITY_MAX_G:                 # 0.5 .. 1.5
            self.state = IMU_OK
        else:
            self.state = IMU_IMPLAUSIBLE
```

Motion is refused the same way a critical battery refuses it (`esp32_driver.py:214-219`):

```python
        if self._imu_bad():
            self._send_motion(0.0, 0.0)
            return
```

And the boot script will not start a mission (`scripts/robot_boot.sh:349-358`, abridged):

```bash
case "$imu_line" in
  "esp32_driver: imu ok"*) echo "=== [robot-boot] ${imu_line#esp32_driver: } ===" ;;
  "") echo "FATAL: no IMU verdict from esp32_driver within 15s -- not starting a mission" >&2; exit 1 ;;
  *)  echo "FATAL: ${imu_line#esp32_driver: } -- ... switch the robot off and on again" >&2; exit 1 ;;
esac
```

**Verified.** A power-cycle restarted the chip (`ax 8..156, gz -1..11`, gravity 1.05 g).
On the robot the driver then logged `imu ok (gravity reads 1.05 g)` two seconds after
start, in all four runs that followed. **Not verified live:** the frozen case on the new
driver. Mike power-cycled the robot while I was running that test, which was the right
thing to do and cut it off. It is covered by tests built from the captured values.

**Lessons.**
- A sensor that is wired, answering and streaming can still be dead. "Is it changing?"
  and "does it feel gravity?" are two cheap questions to ask before trusting it.
- When a fix is a guess, put a tripwire in front of the retest. The second bad start
  cost one second of motion, not a spin.
- This is the same family as the chassis type and the battery: a fact everything
  downstream took on trust.

## 3 — The dresser: the guard's first real save, and nothing behind it

**The issue.** On trip 1 of the first ball run the robot drove at the dresser's foot.
Mike: "maybe it was off a little from home, but I would have expected it to correct."

**How it was found.** The driver log, the bag and the mast camera together.

```
8.7 s   obstacle_guard: something 0.18 m ahead of the bumper — robot HELD
9-18 s  Nav2 command 0.30 m/s forward, 0.13 rad/s; wheels 0.00; gyro 0.00
18-19 s gyro 0.33 rad/s with the wheels still at 0.00      <- turned by hand
21.0 s  obstacle_guard: path clear — robot RELEASED
```

The mast camera shows the dresser foot filling the right of the frame and Mike standing
up one second before the gyro moves. He confirmed: "I did move it by hand."

**What it means.** The guard did its job: no contact, on its second day. Nothing else
did anything. Nav2 commanded straight ahead into held wheels for ten seconds and would
have gone on until its progress checker gave up. There is no backing away and no
re-planning: steps 6c and 6d, now with a real case.

**Why a slightly-off start fails and a slightly-off return does not** (Mike's question).
Between trips the robot keeps its running position estimate, so an error after a trip is
a *known* error and the next plan starts from it. At the start of a run the estimate is
reset to the configured home pose whatever the robot's real position is; an error there
is *unknown*, and the estimate only corrects as the lidar sees the robot move. The
dresser is 1.7 m and six seconds from home. I could not confirm from the bag that this
start was off; trips 2 and 3 and the earlier run's trip 1 all cleared the dresser.

**Not fixed.** A start-pose check (first scan against the map, before moving) is on the
list.

**Lesson.** A stop is half a behaviour. The other half is what happens next.

## 4 — No ball reaction in daylight: what the camera sees depends on the light

**The issue.** First run with reactions on, 2 pm, sun in the room. Three complete trips;
neither the yellow nor the red ball caused a reaction. Mike: "It does not seem to be
detecting the balls."

**How it was found.**

1. *The mast camera* showed both balls placed correctly, ahead and to the right of the
   path, and showed the yellow ball leaving the front camera's field of view to the
   right as the robot passed it.
2. *The detector's own output in the bag*: yellow seen at 52 px (reads 1.8 m), then
   108 px (0.85 m) at the edge of the frame, then gone. Red: one 16 px blip.
3. *A calibration session* at the previous night's position, balls at 0.50, 0.80, 1.05
   and 1.55 m, window behind them:

   | Ball | Lamp (2026-11-19) | Daylight | Band then in use |
   |---|---|---|---|
   | Red hue | 352-358 | about 330 (324-337) | 340 to 16 |
   | Red saturation | 0.57-1.0 | 0.36-0.51 | min 0.45 |
   | Yellow hue | 36-38 | 43 | 28-46 |

   Red was missed at all four distances. Yellow was found but read 10-30% too far
   (0.65, 0.88, 1.35, 1.70 m) because its lit rim fell out of the band.
4. *Curtain closed, 0.80 m:* it flipped. Red found; yellow merged with the wall behind
   it into one blob 347 px wide, which the shape test rejected.

**Three ideas that did not work, each measured.**

| Idea | Result |
|---|---|
| Lock the camera's white balance | Red's hue swing between the two lights grew from 19 deg to 51 deg. The light itself changes colour; automatic white balance was partly compensating |
| Widen the red band | Red found at 0.50 and 0.80 m only, and a false red in the ball-free photos read 1.36 m (the reaction line is 1.3 m) |
| A bigger thin-bridge eraser | Rescued yellow behind the curtain, and turned a patch of floor into a "ball" 0.37 m away |

**Also tried, for Mike's question about small models.** The vision model already on the
Jetson (`moondream:1.8b`), asked to describe 11 crops: ball or not, 11 of 11; yellow,
3 of 3; red, 1 of 3 ("dark red", "dark purple", "dark brown"); 1.2-2.5 s per crop. It
only answers the plain prompt "Describe this image." (the canary's own note says so;
two other prompts returned empty strings). It is a good judge of "is this a ball" and no
better than the colour band at seeing through the light.

**Lessons.**
- One lighting condition is one data point. The profile's own header said so.
- Before tuning a threshold, look at the mask. The masks showed the detector was
  selecting the right pixels and losing on shape, which pointed at the fix.
- A test of an idea is cheap when the scene is still set up. Three ideas were ruled out
  in ten minutes.

## 5 — The fix: a ball rests on the floor (red reacted; yellow missed by one frame)

**The idea.** A ball sits on the floor and the camera is at a fixed height, so a nearer
ball is both wider in the picture and lower in it. Its bottom row is a straight-line
function of its width, whatever the light does to its colour.

**Measured.** 18 real sightings (lamp, daylight, curtain; 0.5-1.55 m; both colours):
`bottom_row = 325 + 1.32 * width`, within 26 px under the final settings. 51 false blobs
from 52 ball-free photos: one within 30 px of the line, and every one that read close
enough to cause a reaction 75-359 px off it.

**The fix.**

*Before* (`hsv_detect.py`, in `_largest_ball_shaped_blob`): one roundness test, and the
largest blob in the frame wins.

```python
        if max(width, height) / min(width, height) > shape['max_aspect']:
            continue
```

*After* (`hsv_detect.py:168-178`):

```python
        flat_limit = shape['max_flat_aspect'] or shape['max_aspect']
        if width >= height:
            if width / height > flat_limit:          # top lost to glare: full width,
                continue                             # lower half only -- allowed
        elif height / width > shape['max_aspect']:
            continue
        if floor is not None:
            expected_bottom = floor['row0'] + floor['slope'] * width
            if abs((box[0].stop - 1) - expected_bottom) > floor['tolerance_px']:
                continue                             # right shape, wrong height: not a ball
```

*Before* (`hsv_realcam.yaml`):

```yaml
  red:    {h: [340, 16], s_min: 0.45, v_min: 0.08, range_k: 80.3}   # wraps through 0
```

*After* (`hsv_realcam.yaml:28`, `:46`, `:58-61`):

```yaml
  red:    {h: [315, 16], s_min: 0.26, v_min: 0.08, range_k: 80.3}   # wraps through 0
...
  max_flat_aspect: 1.8
floor:
  row0: 325
  slope: 1.32
  tolerance_px: 40
```

The wide red band is safe only because of the floor section; the simulator's profile has
neither and is unchanged.

**Scored on every frame on disk** (`reports/camera_cal_20261120_day/score.py`):

| | 2026-11-19 profile | Today's |
|---|---|---|
| Yellow found (9 frames) | 8 | 9 |
| Red found (9 frames) | 5 (0 of 4 in daylight) | 8 (4 of 4 in daylight) |
| Nearest false yellow, 52 ball-free photos | reads 1.00 m | reads 3.06 m |
| Nearest false red | reads 3.09 m | reads 1.46 m |

**Verified on the robot**, with the detector mounted over the image
(`ROBOT_BOOT_DETECTOR`) after proving the mount inside the container first:

| Trip | Detector | Outcome |
|---|---|---|
| 1, no ball (twice) | nothing false on the way out | full trip |
| 2, yellow | 22 frames in a row, 3.3 m down to 0.53 m | **no reaction**: readings 0.86, 0.84, 0.84, then 0.60 and 0.53. Two inside 0.8 m; the rule needs three; the robot arrived |
| 3, red | tracked from 2.6 m; 1.20, 1.20, 0.89 inside 1.3 m | **reaction fired**: goal cancelled, photo, stop |

Mike: "Overall success ... It finally stopped about 58 cm from the red ball." The
detector's last reading before the stop was 0.62 m.

**Not done, and not hidden.**
- Yellow did not react. At about 3.6 frames a second, three frames is roughly 25 cm of
  travel, and yellow reads about 10% far in daylight. Two frames, or 0.9 m for yellow,
  would have fired. The rule is shared with the simulator and was not changed today.
- Red fires later than its nominal 1.3 m for the same reason (it reacted on a 0.89 m
  reading).
- Under lamp light the wide red band reads near (0.80 m as 0.67) and misses red at
  1.05 m: a step back from the night before at that one distance.
- A false red 1.46 m away remains in one lamp-light photo.
- The detector finds nothing in the saved reaction photo although it found the ball in
  the live frames a second earlier. Not looked into.
- The floor line was fitted with the robot standing still. A moving robot pitches.

**Lessons.**
- When two things will not separate on the property you are measuring, find a property
  that comes from physics. Yesterday it was shape; today it was where a ball can be.
- "Biggest blob" is a tie-break, not a test. Choosing the blob that fits the rule made
  wider bands safe.
- A reaction rule has a frame rate in it. "Three frames" is a distance.

## 7 — The WiFi changed its address and the mission died at the marker

**The issue.** Second ball run. Mike: "It started to turn, beeped and stopped."

**How it was found.** The guard had not held anything. Every node's log was full of
`ddsi_udp_conn_write to udp/192.168.1.112 ... failed`, and the Jetson was now at .126.

| Time | Event |
|---|---|
| about 15:17 | Ethernet unplugged for the run |
| 15:18:38 | trip 1 reaches the marker and starts for home |
| 15:18:52 | WiFi re-does its handshake with the router |
| 15:18:58 | new address .126 (was .112); every node's sockets are dead |
| 15:18:59 | the driver's command watchdog stops the wheels |
| 15:19:00 | operator watch pauses for the 2 s gap, then releases |

The same thing had happened at 13:49: a new address about a minute after the Ethernet
came out (.120 to .112). Two for two; an observed pattern, not a proven mechanism.

**What it means.** The robot stopping was the fail-safe working. The mission dying was
wrong: the robot's own nodes were talking to each other through the WiFi adapter. Mike:
"If this is supposed to be an autonomous vehicle, loss of wifi should not be fatal."

**Not fixed today.** The design agreed in conversation:
1. the robot's own messaging on loopback, never on WiFi;
2. monitoring one-way and best-effort, with local recording as the record;
3. safety on board (guard, battery, board stop-on-silence, switch); remote stop is a
   convenience;
4. link loss as a per-run policy: pause-and-resume (attended, today's behaviour),
   carry on (unattended), carry on then come home (long tours).

**Also found.** With messaging dead, `robot_boot.sh` exited and left the whole driver
layer orphaned; five processes needed a hard kill, and a stale `ros2` daemon hung on its
old sockets. `jetson.local` stopped resolving for a while after the address change.

**Workaround used.** Wait until the address has settled after pulling the Ethernet. The
rerun then completed.

**Lesson.** "Needs no network" has to be true of the plumbing, not only of the mission.
