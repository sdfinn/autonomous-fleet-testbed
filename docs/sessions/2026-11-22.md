## 1 — Two projects on one workstation: each one's CI killed the other's processes (fixed)

**Issue.** This workstation runs this repo's CI, wayfarer's CI and local simulators.
Both projects' Nav2 and EKF processes have the same names, and both ran on ROS domain
0. Every sweep here was a `pkill -9 -f <name>`.

**How found.** Mike asked whether he could work on both projects at once. Reading both
repos' CI files showed each one killing the other's processes by name, and two runner
services (`~/actions-runner`, `~/actions-runner-sf`), so both pipelines can run together.

**Fix.** Wayfarer moved to domain 42 (its own session). Here, every by-name kill goes
through a new tool that reads the environment each process was started with:

```python
# tools/proc_sweep.py:107
def is_ours(proc, domain):
    """True when `proc` was started on `domain` (see the module text for the rule)."""
    if proc.domain is UNREADABLE:
        return False
    if proc.domain is None:
        return domain == DEFAULT_DOMAIN
    return proc.domain == domain
```

Before, in `ci.yml` (three places), `scripts/hil_stage.sh` and `tools/mission2_day.py`:

```
pkill -9 -f "parameter_bridge|component_container_isolated|ekf_node|ball_detector" || true
```

After (`.github/workflows/ci.yml:302`, `:388`, `:507`; `scripts/hil_stage.sh:522`;
`tools/mission2_day.py:407`):

```
python3 -m tools.proc_sweep "parameter_bridge|component_container_isolated|ekf_node|ball_detector" || true
```

The tool also never matches its own shell or its parents (`self_and_ancestors`,
`tools/proc_sweep.py:82`), which removes the `pkill -f` self-kill trap of 2026-11-20.

**Verified.** 12 tests, one with two real processes on domains 0 and 42. Then for real:
CI run `45060191707` here and wayfarer's `45060634456` overlapped; this repo's log shows
its own leftovers killed and wayfarer's `ekf_node`, `component_container_isolated` and
`robot_state_publisher` printed as "left alone, not on domain 0". Both runs green.

**Lesson.** A process carries the environment it was started with for its whole life
(`/proc/<pid>/environ`). That is a cheaper and more exact way to say "mine" than a name.

## 3 — Choosing the detector: what pretrained detectors do on our own pictures

**How.** `reports/detect_exp_20261122/exp.py` (outside git) ran seven pretrained
detectors on the frames that scored the hand-written one, then on simulator photos,
then on five new arrangements of dog toys and clutter photographed by the robot's front
camera. Full tables: `docs/detection-history.md`.

**What was learned.**
- **Finding and naming are different results.** Every detector boxed nearly every ball.
  The yellow croquet ball was "orange" 26 times, at up to 0.92.
- **A score is not "how sure it is right", and a detector never says "unknown".** A
  furniture foot was "toilet" at 0.87; a wallet and a watch were "remote". The brain
  must expect three cases: a known object, a boxed object with an untrustworthy name,
  and an object nothing reported (a sock lying flat, dark shoes, a toy in shadow).
- **Plush dog toys are found as "teddy bear"** with no training.
- **A larger picture is not better:** the YOLO models named balls better at the 640
  pixels they were trained at than at 1280.
- **The simulator is the easy case,** and a simulator result does not predict the
  robot: the detector that was best on real frames when prompted with words was the
  worst on rendered ones.
- **The describer** (`moondream` on Ollama) turns a wrong name into a right one for 22
  of 25 ball crops with "Describe this image.", and answers nothing at all to "Is this
  a ball? Answer yes or no."

**Decisions (Mike).** RF-DETR small for anything that ships (Apache-2.0, like this
repo). YOLO models (AGPL-3.0) for comparison and labeling on the workstation only. No
training for now.

## 5 — The detector node: built, and what the bench test caught

**Built.** `rfdetr_detect.py` (arithmetic), `rfdetr_backends.py` (TensorRT engine or
ONNX Runtime behind one interface), `object_detector.py` (the node; shadow mode on
`/robot_001/detections_shadow`), `config/detector_rfdetr.yaml`, a switch in
`scripts/robot_boot.sh:365` (`ROBOT_BOOT_SHADOW_DETECTOR=1`), and
`tools/shadow_compare.py` to compare the two detectors from a run's bag.

**Verified.** Our code against the `rfdetr` package's own answer on the five toy
frames: 43 of 44 boxes match on the workstation and on the Jetson's GPU. Live on the
Jetson's camera: 10 pictures a second, about 40 ms of work each.

**Problem 1: 76 ms a picture when the network takes 13.**
*How found:* timing each stage separately on the Jetson. The plain-numpy resize of the
1280 x 720 picture took 62 ms. *Fix:*

```python
# src/nav_fleet/nav_fleet/rfdetr_detect.py:112
    cv2 = _opencv() if use_opencv else None
    if cv2 is not None:
        return cv2.resize(np.ascontiguousarray(rgb), (width, height),
                          interpolation=cv2.INTER_LINEAR).astype(np.float32)
```

OpenCV does the same resize in 8 ms; the numpy version stays as the fallback and a test
holds the two to the same result. *Lesson:* time each stage before trusting a total.

**Problem 2: the rug was still a "bed".**
*How found:* the first live message from the node carried a 1275-pixel-wide "bed" box
at a score of 0.49. I had set the size filter from memory at 50% of the picture; that
box covers 41%. *Fix:* `max_box_fraction: 0.35` (the real bed covers 17-20%), with the
measured sizes written beside it.

```python
# src/nav_fleet/nav_fleet/rfdetr_detect.py:199
        if (x1 - x0) * (y1 - y0) > cfg['max_box_fraction'] * width * height:
            continue                           # "the rug is a bed": not an object on the floor
```

*Lesson:* check a filter against measured sizes, not a remembered one.

**Problem 3: two-thirds of a processor core.**
*How found:* `top` during the live run. Each 2.7 MB picture was copied twice before the
network saw it. *Fix:* `image_msg_to_array` (`object_detector.py:98`) reads the message
without copying, and the color channels are swapped after the resize, on the small
picture (`prepare(..., bgr=True)`, `rfdetr_detect.py:132`). 64% of a core became 36%.

**Also learned:** a picture is about 0.35 s old when its detections go out, nearly all
of it inside the camera's own pipeline. At 0.3 m/s that is about 10 cm of travel.

## 6 — The conversation: a goal, a vocabulary, and a list

**Issue.** "Brain", "model" and "tree" each meant two or three things during the day,
and I called wayfarer's hard-coded behavior tree a brain. Mike: "A first brain with no
model in it makes no sense."

**Result** (`docs/terminology.md`):
- **The goal:** the robot boots and loads everything; it can then carry out any
  mission; a mission is given as a mission script or, preferred, as a request in plain
  English to the brain, and the robot makes the judgment.
- **The words:** reflexes; state estimation; navigation and Nav2's behavior tree;
  detector; describer; skills and the plan; mission logic as a mission script (here) or
  the mission's behavior tree (wayfarer only); brain = a language model on Ollama that
  chooses the plan and makes judgments, built in neither project yet.
- **The rule:** goals go down, events come up; the lower layers do not care who sent
  the goal. The brain takes over the plan, not the skills.

**The draft list** (`docs/goals-and-events.md`, milestones M1 to M6) showed what blocks
installing wayfarer's mission's behavior tree here: it turns, drives short distances and
backs up through three Nav2 actions that fail on the real robot ("Pose Goes Off Grid");
the reflexes' holds reach nothing above them; the detection message is about to change.

**Also agreed:** nothing loads during a mission. Detector required before "go";
describer required or optional per mission; a question to the describer has a time
limit, and no answer, an empty answer or a useless answer all mean "unknown object".

## 8 — The floor run in shadow mode: the hand-written detector is three seconds behind

**The run** (17:03, lamp light at night, WiFi, pack 11.81 V): the normal three-part
Mission 2 day with `ROBOT_BOOT_SHADOW_DETECTOR=1`. Exit 0, clean shutdown, start pose
0.00 m from home. Part 1 (no ball) passed; part 2 (yellow) drove past the ball with no
reaction; part 3 (red) reacted. Evidence: `reports/robot_boot_20261122_shadow/` (bag,
logs, `shadow_compare.txt`). The new switch, the node and the comparison tool all
worked on their first real run.

**Found: the yellow reaction's real cause.** `tools/shadow_compare.py` and the bag's
own receive times show how long after a picture was taken its detections were recorded:

| Detector | Median | Best | Worst |
|---|---|---|---|
| Hand-written (in the container) | 3.06 s | 2.13 s | 3.51 s |
| RF-DETR (shadow, on the Jetson) | 1.03 s | 0.46 s | 1.66 s |

On the yellow approach the hand-written detector had the ball inside 0.8 m in NINE
pictures in a row, taken from 13.1 s to 15.3 s into the part. Their detections arrived
from 16.4 s to 18.6 s. The robot reached the marker and the leg ended at 17.35 s. At
0.3 m/s, three seconds is about 0.9 m of travel: the mission script is reacting to
where the ball was three seconds ago.

**Likely cause (not yet tested).** The hand-written detector takes about 0.24 s a
picture (4.2 a second) and the camera sends 10 a second, and its subscription keeps a
queue of 10 pictures:

```python
# src/nav_fleet/nav_fleet/ball_detector.py:35
        self.create_subscription(Image, '/robot_001/camera/image_raw', self._image_cb, 10)
```

A consumer slower than its source with a queue of 10 always works on the oldest of 10
waiting pictures: 10 pictures at 4.2 a second is 2.4 s, plus the camera's own 0.35-0.45
s and one processing time, which is the 3 s measured. The new node keeps a queue of 1
for exactly this reason (`object_detector.py:138`) and is 2 s fresher. The 2026-11-20
explanation ("two frames inside 0.8 m, three needed") described the symptom; it also
explains why red stopped 58 cm from a ball it reacts to at 1.3 m.

**Lesson.** Measure when an answer arrives, not only what it says. A count of frames
or a rule in seconds cannot fix an input that is three seconds old.

**The two detectors on the same pictures:**

| | Hand-written | RF-DETR (shadow) |
|---|---|---|
| Part 1, no ball on the floor | "red" in 60 pictures and "yellow" in 16; three reds inside the 1.3 m reaction distance, never three in a row | no ball-like box at all |
| Part 2, yellow ball | 55 pictures, nearest 0.35 m | ball-like in 55 pictures ("sports ball" 45, "orange" 34), nearest 0.55 m; distance agrees with hand-written to 0.02 m (median) |
| Part 3, red ball | 36 pictures, nearest 1.04 m | ball-like in 33 pictures ("apple" 28, "sports ball" 16), nearest 0.65 m; reads 0.31 m farther than hand-written (median) |
| Pictures a second during the mission | 4.2 | 5.3 (9 in the dry check with no mission running) |

RF-DETR also boxed a person in 325 pictures (Mike, watching) and furniture throughout.
Open questions from this table: whether the balls in Mike's hands were in view during
part 1 (that would make some of the hand-written "false" detections real balls off the
floor); which red distance is right (the hand-written red is known to read near under
lamp light); and why the node gets about half the pictures once the mission container
is running.

## 10 — The switch: RF-DETR becomes the robot's detector

**Decision (Mike, after the two runs):** stop comparing against the hand-written
detector; make RF-DETR the detector on the robot now and tune that. Bring the simulator
and CI onto it right after, so the robot and Gazebo do not drift apart.

**What the mast camera and the tape added.** The red stop was about 70 cm from the ball
by tape; RF-DETR's nearest reading was 0.68 m, the hand-written detector's 0.83 m. The
mast video (`reports/robot_boot_20261122_q1/q1_20261122.avi`) shows the robot stopping
for red at a clean moment and, for yellow, the reaction arriving about two seconds
before the trip would have ended anyway: with the yellow ball 0.3 m past the marker and
a 0.8 m reaction distance, a reaction and a normal arrival look the same to someone
watching. It also caught the dog in the living room; RF-DETR boxed him as "dog" 58
times (up to 0.90) from the front camera.

**The problem with a plain switch.** RF-DETR does not know yellow from red: both balls
are "sports ball", or "orange" and "apple". The mission reacts differently to each.

**Fix: read the color inside the box** (`ball_color`, `rfdetr_detect.py`). Finding a
ball BY color is what failed in three sessions; telling two colors apart INSIDE a box
the network already drew is a far easier question. Only the middle of the box votes,
and only pixels with enough color to have a hue:

```python
# src/nav_fleet/nav_fleet/rfdetr_detect.py, in ball_color()
    votes = (saturation >= cfg['color_min_saturation']) & (value >= cfg['color_min_value'])
    if votes.mean() < cfg['color_min_fraction']:
        return None
```

A ball whose color was read is published as `yellow_ball` or `red_ball`, the names the
mission script already reacts to, so the mission script is unchanged.

**Verified on real pictures** (`reports/detect_exp_20261122/color_check.py`): the nine
calibration pictures in three kinds of light: yellow 9 of 9, red 9 of 9, the dark green
ball given no color 9 of 9. Measured inside the boxes: yellow hue 21-51 and red 324-9,
each with 98-100% of the pixels voting. The green ball in dim light read hue 37 with
only 46% voting, which set `color_min_fraction` at 0.7. Known limit: a pink plush pig
boxed as "apple" reads red.

**The plumbing.**
- `nav2_only_launch.py`: new argument `ball_detector` (default true);
  `container_entrypoint.sh` passes `BALL_DETECTOR`. With false, the container does not
  start the hand-written detector.
- `scripts/robot_boot.sh`: `ROBOT_BOOT_RFDETR=1` starts the RF-DETR node publishing
  `/robot_001/detections` and passes `BALL_DETECTOR=false`.
  `ROBOT_BOOT_SHADOW_DETECTOR=1` still gives shadow mode; setting both is refused.
- The hand-written detector stays the detector in the simulator and CI for now, with
  the queue-of-1 fix. **Until RF-DETR also runs there, the robot and CI test different
  detectors.** Closing that is the next job.
