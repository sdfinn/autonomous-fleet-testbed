## 1 — Does a network trained on photographs find Gazebo's plain spheres?

**Issue.** The plan put RF-DETR into the simulator. Nobody knew whether a detector
trained on photographs would call a flat-colored, untextured Gazebo sphere a ball. If
not, the whole of item A needed another design (a textured ball, or training).

**How found.** The cheapest experiment first, before any wiring: the simulator alone,
the robot parked, a ball spawned straight ahead at seven distances and two sideways
offsets in yellow and red, each picture saved, then the detector run on the saved
pictures outside ROS.

**Result.** Every ball from 0.5 m to 2.5 m came back as "sports ball" with a score of
0.73 to 0.94, and the color step named every one correctly using the bands measured on
the REAL camera (Gazebo's yellow is hue 60, its red hue 0). Only the distance constant
differs, because the simulated camera is 640 pixels wide with another lens:

```yaml
# src/nav_fleet/config/detector_rfdetr_gazebo.yaml:17
ball_range_k: 46.5
range_reference_width_px: 640
```

Box width times distance was 44.0 / 45.6 / 46.5 / 46.8 / 46.5 / 48.0 / 47.5 at
0.5 / 0.8 / 1.0 / 1.3 / 1.5 / 2.0 / 2.5 m; the reactions fire at 0.8 m and 1.3 m, so
the constant is taken there.

**Verified.** One Mission 2 day in the local simulator with RF-DETR in control: no
ball, yellow and red all PASS (`reports/sim_rfdetr_20261123/day1/`).

**Lesson.** When a plan rests on one unknown, test that unknown alone before building
on it. Twenty-five saved pictures answered in four minutes what a wired-up mission
would have answered in an hour, and less clearly.

## 2 — `ros2 launch` runs nodes with the system Python, not the virtual environment

**Issue.** Yesterday's plan said "ONNX Runtime into `fleet-env`". The detector node
started from a launch file would not have found it there.

**How found.** Before writing the launch change, the launcher's first line:

```
$ head -1 install/nav_fleet/lib/nav_fleet/object_detector
#!/usr/bin/python3
```

A colcon build writes the launcher with the Python that ran the build, which is the
system's. `fleet-env` is only used by the tools and tests started by hand.

**Fix.** ONNX Runtime installed user-level for the system Python, WITHOUT its
dependencies. A dry run showed a plain install would also put a new `protobuf` in
`~/.local`, in front of the one ROS and Gazebo use:

```bash
/usr/bin/python3 -m pip install --user --break-system-packages --no-deps onnxruntime
```

CI's simulator stage now checks for the two things that live outside the repo and
says so, instead of failing later as a missed reaction:

```yaml
# .github/workflows/ci.yml:321
test -f "$HOME/fleet-ci-data/models/rfdetr-small.onnx" || { echo "FATAL: RF-DETR model file missing: ..."; exit 1; }
/usr/bin/python3 -c "import onnxruntime" || { echo "FATAL: the system Python has no onnxruntime (...)"; exit 1; }
```

**Verified.** A detection run under `/usr/bin/python3` (75 ms a picture, numpy 1.26
untouched), then the launch itself.

**Lesson.** "Installed" is a statement about one interpreter. Look at which Python a
process really runs under before installing for it; and dry-run an install into a
shared interpreter to see what else it would bring.

```python
        return
    log.info('retreat detected — placing yellow behind the returning robot')
    holder['placed_name'] = ball_ops.place('yellow', *ball_xy)

        return
```

## 10 — CI's unit-test stage hung; behind it, a shutdown race in `robot_boot.sh`

**Issue.** After the push of the two commits above, CI's stage 1 (unit tests, on a
GitHub-hosted machine) sat in "Run Python unit tests" for 19 minutes; it normally
takes 5. **Mike noticed it** ("that does not seem right?") and then gave the clue that
located it: the last line printed was
`test_attended_run_starts_the_watch_and_makes_it_mandatory_for_the_driver PASSED`,
so the next test in that file was the stuck one:
`test_attended_run_ends_when_the_watch_gives_up`.

**How found.** It passed here every time, even pinned to one processor core. With four
busy loops competing for that core it got stuck in 4 to 6 of every 8 to 12 runs: a
race, not a property of the hosted machine. Three layers came apart one at a time:

1. *Why CI hung instead of failing.* On a timeout the test killed the script's own
   process group and then read its output with no limit. The script starts its
   long-running jobs in their OWN process groups (`set -m`), so they survived, kept the
   pipe open, and the read never ended.
2. *Where the script was stuck.* With the harness fixed to print the process tree
   before killing anything: the mission container, bag, drivers and detector were all
   still alive. Cleanup had not started.
3. *The line.* A per-process shell trace of a stuck run ended at:

```
+robot_boot.sh:1:   exit 131
+robot_boot.sh:1:   cleanup
+robot_boot.sh:125: kill 232419
+robot_boot.sh:125: true            # kill failed: the waiter had already exited
+robot_boot.sh:126: wait 232419     # never returns
```

**Cause.** When the operator watch ends, a small waiter process signals the script
(`kill -USR1 $$`) and then exits by itself. Cleanup killed the waiter and then waited
for it. If the waiter was already gone when cleanup reached that line, the `wait`
never returned. An idle machine reaches the line first; a busy one does not.

**Why it matters beyond CI.** This is the real robot's path for "the operator's link is
gone for good: stop the mission". The wheels would still be held (the driver holds
them once the watch is gone), but the script would hang with the mission container
alive, the bag unfinalized and the drivers running. It predates today's work: the tree
from before today's script change hung 6 times in 8 under the same load.

**Fix.**

```bash
# scripts/robot_boot.sh, cleanup(), before
if [ -n "$WATCH_WAITER_PID" ]; then
  kill "$WATCH_WAITER_PID" 2>/dev/null || true
  wait "$WATCH_WAITER_PID" 2>/dev/null || true
fi
# after: nothing needs the waiter's exit status, and USR1 is ignored by then
if [ -n "$WATCH_WAITER_PID" ]; then
  kill "$WATCH_WAITER_PID" 2>/dev/null || true
fi
```

And three guards so a hang cannot sit silently again:

- `tests/test_robot_boot_script.py`, `_finish()`: on a timeout, record the process
  tree, kill the whole SESSION (every process group the script made), read the output
  with a limit, and fail with both.
- CI stage 1: `--timeout=180` per test and `timeout-minutes: 20` for the job.

**Verified.** The two watch tests, 16 runs under the same load: 16 passed (before: 4 to
6 stuck per 8 to 12). The whole script test file: 46 passed.

**Not verified.** Whether the other `wait`s in the shutdown (for jobs that are still
alive when they are signalled) can meet the same fault. They did not in 16 loaded
runs. The give-up path has still never been seen in a real mission.

**A wrong turn of mine.** My first explanation was plain slowness: one more job to
stop since today's change, a 20 s limit, a slow machine. The measurement refuted it:
runs took either 3 s or forever, nothing in between, and the old tree did the same. I
had also run one comparison whose load had expired before the second half, and nearly
read "8 of 8 passed" as evidence.

**Lessons.**
- A test that waits without a limit turns a failure into a hang, and a hang carries
  no message. Every wait in a test harness needs a limit and something to print.
- Before killing a stuck process, photograph it: the process tree named the layer in
  one look.
- Durations that come in two clumps mean a race or a deadlock, never "slow".
- "It passes on my machine" was true and useless. Starving the test of processor time
  reproduced the hosted machine's failure in minutes.
- Check that the stress is still on when the measurement ends.

## 11 — The simulator stage after the fix: two marginal checks, and the stall reproduced at last

**CI run `45245579657` on `6127dd0`.** Stage 1 passed in 5 minutes (the hang is gone).
Stage 2 failed twice, on two different checks:

- attempt 1: the first-drive stall again, now with its position (section 8);
- attempt 2: the smoke test's `ball_correlation`, lidar half. The lidar read 0.643 m
  for a ball "0.75 m away"; the tolerance is 0.102 m (`tools/smoke_test.py:58`). Four
  earlier CI runs read 0.666 to 0.669 every time. The check compares a range measured
  to the ball's near SURFACE from the LIDAR with a distance defined center to center
  from the robot's middle, so geometry uses about 8 of its 10 cm. It has always run
  with 2 cm to spare; a 2.4 cm outlier failed it. The detector's half passed.

Three stage-2 failures in five CI attempts in one day is too many to call luck, so I
looked for what today added to that stage.

**The detector's processor use.** Measured at the camera's pace on the 32-thread
workstation:

| ONNX Runtime setting | ms a picture | cores busy |
|---|---|---|
| defaults | 66 | about 16 |
| 8 threads, spinning | 74 | 7.8 |
| 8 threads, no spinning | 80 (worst 93) | 5.1 |
| 4 threads, no spinning | 117 | 4.3 |

The defaults buy 14 ms for 11 cores: its worker threads spin while they wait. Fixed
(`rfdetr_backends.py`, `ONNX_THREADS = 8`, `onnx_session_options`), commit `120ad2e`.

**The CI service has no display.** `/proc/<runner pid>/environ` has no `DISPLAY`, so
in CI Gazebo renders the camera and the lidar in software on the processor. My local
copies of the stage ran from a shell WITH a display, on the graphics card. Run without
one (`env -u DISPLAY -u XAUTHORITY -u WAYLAND_DISPLAY`), the local copy failed on
`test_navigation_succeeds` at once, and the detector slowed from 82 ms to about 110 ms
a picture. **That was the missing difference between "passes locally" and "fails in
CI".** The thread cap was already in place for that run, so the detector's load is not
the whole cause of the stall.

**What the stall is.** One no-display drive with `/robot_001/cmd_vel` recorded
(`reports/sim_rfdetr_20261123/stall_1/`): from 15 s on the forward command is exactly
0 and the turn command is a regular wave, -0.5 to +0.5 rad/s and back every 0.8 s, 124
reversals in 50 s. The robot is turning on the spot, back and forth, 0.17 m from the
goal (goal circle 0.15 m), until the progress rule ends the goal. Not a wedge, not a
crawl: a limit cycle in the path follower's "rotate toward the path" step when the end
of the path is beside the robot.

**Two of my guesses that the evidence killed today:** "wedged at the doorway" (the
position line) and "the approach speed is too low to move the robot" (the recording).

**A third that did not survive a repeat.** `FollowPath.max_angular_accel` was raised
from 3.2 to 10.0 on 2026-11-19 for the real robot, and the stall was first seen on
2026-11-20. With 3.2 the drive passed 3 of 3; with 10.0 it had stalled 2 of 2. Then,
back on 10.0 for an A-B-A check, it passed 2 of 2. So: not established on five runs. A
batch of 8 drives each, alternating, then gave numbers. All no-display first drives of
the day together (`reports/sim_rfdetr_20261123/batch_accel.txt` and the runs before it):

| `max_angular_accel` | stalled | passed |
|---|---|---|
| 10.0 (ours since 2026-11-19) | 5 of 13 | 8 |
| 3.2 (Nav2's default) | 0 of 11 | 11 |

If both settings stalled equally often, 0 of 11 would happen about 3 times in 100
(Fisher's exact test, one-sided, p = 0.03). Good evidence, not proof, that the higher
limit lets the path follower fall into its left-right turning near the goal. NOT
changed: 10.0 was chosen to stop the real robot sweeping 16 to 37 degrees past its
final heading, so 3.2 would trade a simulator fault for a real-robot one. Options for
Mike, after the existing-solution check: a value for the simulator only; a value in
between, tested both ways; or the cause, which is how the follower finishes a path
when its end is beside the robot.

**Lessons.**
- Find out HOW the CI machine differs before believing "it passes locally". Here it
  was one environment variable, and it decided whether a graphics card or the processor
  drew every camera picture and lidar scan.
- Run A again after B. Three passes after two failures looked like a result and was not.
- A library's default thread count is a decision somebody else made for a machine that
  runs nothing else.
- A check with 2 cm of margin will fail; the question is only when.

## 12 — The turning stall: cause found in Nav2's source, fixed with Nav2's own setting

**Where the earlier sections left it.** A robot turning left and right on the spot
0.17 to 0.22 m from its goal; reproducible without a display; `max_angular_accel`
implicated by numbers (5 of 13 against 0 of 11) but not understood.

**The existing-solution check, done by reading.** The path follower is Nav2's
Regulated Pure Pursuit controller, version 1.3.12 here. Its source, three functions:

```cpp
// regulated_pure_pursuit_controller.cpp (Nav2 1.3.12), shouldRotateToGoalHeading()
double dist_to_goal = std::hypot(carrot_pose.pose.position.x, carrot_pose.pose.position.y);
if (params_->stateful) {
  if (!has_reached_xy_tolerance_ && dist_to_goal < goal_dist_tol_) {
    has_reached_xy_tolerance_ = true;     // latched: never cleared until the next plan
  }
  return has_reached_xy_tolerance_;
}
return dist_to_goal < goal_dist_tol_;
```

Once that is true the controller only ever calls `rotateToHeading()`, which sets the
forward speed to zero. `goal_dist_tol_` is the goal checker's `xy_goal_tolerance`,
0.15 m. So the follower decides "position reached" for itself, once, and the goal
checker decides separately on every tick. If the robot is inside the circle for the
follower's one look and outside afterward, each waits for the other.

**Confirmed by recording the follower's own topics** during a stall
(`reports/sim_rfdetr_20261123/latch_1/`; `/robot_001/lookahead_point` is the very
point whose distance is compared):

```
t 10.93 s  turning on the spot -> True     distance 0.156 m
around the minimum:  0.151 0.149 0.145 0.144 0.144 0.144 0.150 0.152 0.153
during the stall:    0.163 m, constant
```

It latched with 6 mm to spare and the robot ended 13 mm outside. The left-right
swinging is only what "turn to the goal heading" looks like with our acceleration
limit: the controller's own slow-down rule is `sqrt(2 * max_angular_accel * angle)`,
which with 10.0 does not bite until under a degree, so the command flips between +0.5
and -0.5 rad/s. That is why 10.0 made stalls more likely without being their cause: a
rougher turn moves the robot or the localization estimate by the centimeter it takes.

**Fix.** Nav2's own setting for exactly this, not a workaround:

```yaml
# src/nav_fleet/config/nav2_params.yaml:197, under controller_server.FollowPath
stateful: false
```

With it the follower drives back in whenever it finds itself outside the circle. The
goal checker keeps its own latch (`goal_checker.stateful: true`), so the goal still
ends the moment the robot is inside.

**Verified.** First drive on a fresh simulator, no display, acceleration limit 10.0:

| follower `stateful` | stalled | passed |
|---|---|---|
| true (Nav2's default) | 6 of 14 | 8 |
| false | 0 of 13 | 13 |

(p = 0.01, Fisher's exact test.) Drive times unchanged, 12.4 to 12.8 s. The whole stage
without a display: 42 tests, the Mission 2 day and the smoke test PASS. Pinned by
`tests/test_nav2_params.py`. Commit `3d0239b`.

**Not verified.** The real robot. The setting applies there too (Mike: "fix it
properly, both") and has not run on the floor. On 2026-11-22's floor run the return
from yellow stalled at the door frame under an obstacle hold, which is a different
fault; whether any earlier "stopped short and stood" on the real robot was this one is
not known.

**Lessons.**
- When a standard component misbehaves, read its source for the version installed.
  Twenty minutes of reading replaced three wrong guesses and named a setting.
- A correlation can be real and still not be the cause: the acceleration limit changed
  how often, the latch was why.
- Two parts of a system that each decide "done" by their own measurement need to be
  checked for the case where they disagree.

**The cause of "nothing follows a hold" was not a missing behavior.** Two things:

1. *The planner was blind to the lidar.* In the global costmap's obstacle layer the
   lidar source had no `max_obstacle_height`. Nav2's default for a source is 0.0,

   The file's comment said the global obstacle layer had been "restored"; it marked
   nothing.

```yaml
# src/nav_fleet/config/nav2_params.yaml, global_costmap.obstacle_layer.scan (branch)
topic: /robot_001/scan
data_type: "LaserScan"
max_obstacle_height: 2.0      # the missing line
marking: true
clearing: true
```

2. *The plan was made once per goal* (`navigate_simple.xml`), so even a visible
   obstacle could not change it.

**What our obstacle guard does in this** (read from `path_guard.py`, then seen): it is
directional. It blocks while a forward speed is asked for with something ahead, checks
BEHIND while reversing, does not check during a turn on the spot, and releases one
second after the checked side is empty. So Nav2's `BackUp` can move the robot away
under the guard. Nav2's own collision check refused some spins and back-ups into
marked obstacles ("Collision Ahead - Exiting Spin"): the standard check doing its job.

**The branch** `item-b-go-around`, draft pull request #6, commit `d4bb184`:

- `nav2_params.yaml`: the line above; `navigate_to_pose_recovery.xml` as the tree;

  costmaps" recovery (a cleared box is planned through again); header rewritten.

**Verified on the branch** (no display): box in open floor driven around in 19.1 s;
