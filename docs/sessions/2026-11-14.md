## 2 — The robot "wouldn't power on": it was being charged with the Jetson's adapter

**The issue.** The Jetson couldn't be reached over Ethernet or WiFi, and nothing on the
robot lit up.

**Root cause.** The robot had been plugged into the **Jetson's 19.5 V power brick**. The
Waveshare UGV's 3S 18650 UPS pack charges from its own **12.6 V 2 A** charger. One cell
measured 2.7 V, which means the pack was nearly flat. (A healthy 18650 cell reads about
3.6–4.2 V, so about 11–12.6 V for the pack.)

**How it was found.** Mike measured the cells and the charger's barrel voltage with a
multimeter. That ruled out network or software causes.

**The fix.** Charge with the robot's own 12.6 V adapter. After a few hours the lidar was
spinning, the Jetson's light was on, and both SSH paths worked:

- Ethernet: `10.42.0.217`, 0.17 ms.
- WiFi: `192.168.1.113` on the "Vigor" network.

**Lesson.** The two adapters look interchangeable but aren't. **Never put the Jetson's
19 V brick into the robot's charge port.** This hasn't been added to
`RealRobotStartup.md` yet; see "Next".

## 4 — Stage 1 broke without any change on our side: `ubuntu-latest` is now 26.04

**The issue.** `stage-1-quality` failed during apt install:
`Unable to locate package ros-jazzy-ament-flake8`.

**Root cause.** `ubuntu-latest` on GitHub-hosted runners now resolves to **Ubuntu
26.04**. ROS 2 Jazzy's apt repository only publishes packages for **24.04 (noble)**, so
none of the `ros-jazzy-*` lint tools exist for the new image.

**The fix.** Pin the job to 24.04. `.github/workflows/ci.yml:119-122` (CRLF file, edited
with the Edit tool):

```yaml
  stage-1-quality:
    # Pinned to 24.04 (noble): ROS 2 Jazzy's apt repo only publishes for noble, and
    # ubuntu-latest moved to 26.04 by 2026-11, breaking the ament-* lint installs.
    runs-on: ubuntu-24.04
```

`changes` and `stage-0-requirements` stay on `ubuntu-latest`, because they don't
install ROS packages.

**Verified.** Stage 1 passed. Commit `15f9371`, pushed.

**Lesson.** On hosted runners, "latest" changes under you. Pin the OS for any job
that depends on a distro-specific apt repo.

## Open at close — stage 4 hung *after* the missions passed (diagnosed, not fixed)

**What happened.** The "Fetch Jetson Nav2 logs" step ran from 00:13:57 UTC until the job
timeout at 00:29:13. Because of that:

- **Teardown never ran.**
- **The VLM canary's on-Jetson result was not collected.**
- **The mission evidence was not uploaded.**

**Root cause, two parts:**

1. **The copy went over WiFi.** `scripts/hil_stage.sh:121-131` tries mDNS first. Now
   that the Jetson is also on WiFi, `jetson.local` resolves to the WiFi address:
   ```bash
   ip=$(getent hosts jetson.local | awk '{print $1; exit}' || true)   # → 192.168.1.113 (WiFi, 150–300 ms)
   if [ -z "$ip" ]; then
     ip=$(ip neigh show dev enp6s0 | awk '$1 ~ /^10\.42\.0\./ ...')    # → 10.42.0.217 (cable, 0.17 ms) — never reached
   ```
   ROS/DDS traffic still used the Ethernet link, which is why the missions passed. SSH
   and scp used WiFi.
2. **The copy grabs every old log.** `.github/workflows/ci.yml:674` copies every file
   matching the glob:
   ```bash
   scp ... ${JETSON_USER}@${JETSON_IP}:~/autonomous-fleet-testbed/reports/nav2_container_*.log /tmp/hil_stage/ || true
   ```
   On the Jetson the glob matches three DEBUG logs from the 2026-08-13 investigation:
   24 MB, 122 MB and 220 MB. They're root-owned and gitignored, so `hil_stage.sh sync`
   never removes them. Today's own log is 45 KB.

**Proposed fixes (awaiting Mike's OK):**

- (a) `discover()` prefers the `10.42.0.x` Ethernet neighbour and falls back to mDNS.
- (b) The fetch copies only the newest log and gets its own `timeout-minutes`.
- (c) Move the three August logs off the Jetson into the workstation's `reports/` as
  evidence.
- Then commit, ask before pushing, and re-run for a fully green pipeline.

**Still running on the workstation at close:** this repo's orphaned CI HIL stack.
