## 1 — A run could finish with no recording (fixed, proven on the robot)

**The issue.** Run 2 on 2026-11-16 ended 0.55 m from home with no bag, so it could not
be diagnosed.

**The fix.** `scripts/robot_boot.sh:152-178` starts a recorder on the Jetson itself (not
in the container), before the drivers, and refuses to run a mission without it:

```bash
BAG_DIR="$LOG_DIR/bag_${TS}"          # ~/fleet-ci-data/robot_boot_logs/bag_<timestamp>
...
ros2 bag record --all-topics \
  --exclude-regex '.*/image_(raw|rect)(/compressed|/compressedDepth|/zstd)?$' \
  --node-name robot_boot_recorder \
  -o "$BAG_DIR" \
  > "$BAG_LOG" 2>&1 < /dev/null &
```

- Outside the container, so force-removing the container cannot lose it.
- Under `~/fleet-ci-data`, not `reports/`: `hil_stage.sh sync` runs `git clean -fd`.
- `--node-name`: the default name is also the container's failure-bag recorder, whose
  snapshot service must be answered by that recorder only.
- `ROBOT_BOOT_NO_BAG=1` skips it.

**How the exclusion list was found.** The first version excluded raw and
`compressed` images. A camera-only check on the Jetson wrote 89 MB in 17 s: the driver
also publishes `zstd` copies of every image. With those excluded: 600 KB in 15 s.

**Verified.** Tonight's real run: 26 MB for 45 s, finalized, and it contained everything
needed for item 5.

**Lesson.** Check the exact command against the real device before trusting a filter;
the topic list on the robot is not the one I had in my head.

## 2 — Ctrl+C did not stop a real mission (fixed, proven on the robot before motion)

**The issue.** Carried over from 2026-11-16: Ctrl+C did nothing for 25 s. The
container's first process is a plain bash script, and Linux drops SIGINT/SIGTERM for a
container's PID 1 with no handler. `docker run` therefore never returned, and bash only
runs a trap after the foreground command returns.

**The fix.** Everything the script starts is now a background job in its own process
group, and the script `wait`s (`scripts/robot_boot.sh:262-275`), so a trapped signal
interrupts at once and the script decides the order (`:117-135`):

```bash
cleanup() {
  trap '' INT TERM HUP                     # a second Ctrl+C must not cut teardown short
  if [ -n "$MISSION_PID" ]; then
    docker rm -f robot_mission >/dev/null 2>&1 || true   # 1. the thing commanding the wheels
    wait "$MISSION_PID" 2>/dev/null || true
  fi
  stop_job "the bag recorder" "$BAG_PID"                 # 2. SIGINT -> bag finalized
  stop_job "the bare-metal driver layer" "$DRIVERS_PID"  # 3. SIGINT -> clean node shutdown
}
trap cleanup EXIT
trap '...; exit 130' INT
trap '...; exit 143' TERM
trap '...; exit 129' HUP     # SSH session lost: nobody can press Ctrl+C any more
```

**Verified.**
- `tests/test_robot_boot_script.py`: the stand-in `docker run` ignores SIGINT/SIGTERM on
  purpose, like the real container. The signal test hung on the old script and passes on
  the new one; 8 tests pass, full local suite 573 passed (before the SIGHUP case was added).
- On the robot, through a real terminal session, Ctrl+C sent 6 s after the container
  started (before Nav2 was up, so no motion): exit code 130 after 7 s, container gone,
  bag finalized, no processes left.
- During the attended run Mike stopped it; the bag was finalized and nothing was left
  running. Which stop he used was not recorded.

**Not verified.** The SIGHUP handling is tested only with stand-ins; that version never
reached the Jetson.

**Lesson.** A fake that behaves well proves nothing about a signal bug. The stand-in had
to ignore the signal the way the real thing does, and the test had to fail first.

## 4 — Commands typed with quotes on the Jetson did nothing

**The issue.** `'MISSION2_IGNORE_REACTIONS=1 ~/…/robot_boot.sh'` → "No such file or
directory".

**Cause.** I gave the commands in their `ssh host '…'` form. Typed at the Jetson's own
prompt, the quotes make bash treat the whole line as one command name.

**Lesson (mine).** Give commands in the form for where they will be typed, and say which
machine each one is for.

## 5 — The attended run: wheel slip at the rug edge, then a turn a metre early

**Mike's observation.** It struggled to get from the wood floor onto the hallway runner,
tried and turned a little, eventually got on, went down the hallway instead of into the
bedroom; he stopped it. The rear wheels looked to be spinning.

**From the bag** (`analysis/bag_table.py`, half-second rows; lidar = ground truth):

| Bag time | Wheels / position estimate | Lidar |
|---|---|---|
| 16–17 s | Commanded and reported 0.30 m/s | Wall ahead 0.93 → 0.69 m: moved about 0.24 m |
| 17–33 s | Wheels report 0.30 m/s, then stop-and-turn attempts; estimate advances 1.1 m more | Front, left and right ranges fixed for ~6 s; side ranges barely change for the whole 16 s; gyro shows almost no turning |
| 33–36 s | Estimate says "level with the bedroom door": turn right | Gets traction, turns right |
| 37–41 s | Drives toward the "door" | Real speed about 0.24 m/s (commanded 0.27) until 0.10 m from a wall |
| 41–45 s | Still commanding slow forward | Front range stuck at 0.10 m until stopped |

- The EKF's only speed input is the wheel encoders, so spin reads as travel.
- AMCL followed the odometry: its pose went from y = 1.20 to 2.76 while the robot had
  really moved about 0.3 m. It never corrected. A corridor looks the same along its
  length, and the map is borrowed.
- Once on the rug, traction was normal.
- Mike's photo: robot nose-in to the corner at the end of the runner, a bag beside it —
  matching the last lidar readings (0.10 m ahead, 0.30 m left). There is a mirror on
  that wall; whether it is at lidar height was not checked.

**Hardware facts established.**
- Front and rear wheel pairs are driven; the centre pair rolls free (Mike).
- The motor board reports one speed per side (`L`, `R` in `T:1001`,
  `esp32_protocol.py:39-40`, `:248`), so front and rear cannot be compared in software.

**Not fixed.** No slip detection exists. **Hypothesis, not shown:** yesterday's 0.55 m
home error is the same effect.

**Lesson.** Wheel odometry is a measurement of the wheels, not of the robot. Anything
that trusts it needs an independent check, and the lidar already provides one.
